# Deploying Xenix Mail for NexusCare and CodeXenix

Each company runs its own Xenix Mail server on its own VM. Nothing is shared between the two: separate logins, contacts, campaigns and mailboxes, and separate sending IPs, so one company's mail problems can't hurt the other's delivery.

The steps are the same for both servers. This guide uses `nexuscare.com` and `codexenix.com`; replace them with the real domains.

| | NexusCare | CodeXenix |
|---|---|---|
| Mail hostname | `mail.nexuscare.com` | `mail.codexenix.com` |
| Install command | `bash install.sh --domain nexuscare.com` | `bash install.sh --domain codexenix.com` |

## 1. Get two VMs

For each company:

- **OS:** Ubuntu 22.04 or 24.04 LTS, x86-64 (the core image is built for amd64 only).
- **Size:** 2 vCPU, 4 GB RAM (2 GB is the minimum), 40 GB SSD or more.
- **Network:** one static public IPv4 address per VM.

Two things the provider must allow, or mail will not be delivered:

1. **Outbound port 25.** Many clouds block it: Google Cloud always does; AWS, Azure, DigitalOcean and Hetzner do until you ask support to lift it. Check this before you buy.
2. **Reverse DNS (PTR).** You must be able to set the IP's reverse DNS to the mail hostname, for example `203.0.113.10 → mail.nexuscare.com`. Gmail and Outlook reject or junk mail from IPs without it.

Open these inbound ports in the provider's firewall:

| Port | Used for |
|---|---|
| 25, 465, 587 | SMTP: receiving mail, and sending from mail apps |
| 143, 993, 110, 995 | IMAP and POP3 for mail apps |
| 80, 443 | The admin console, webmail, and SSL certificate requests |

## 2. Point DNS at the server

At each company's DNS provider, before installing:

- `A` record: `mail` → the VM's IP (so `mail.nexuscare.com` resolves to the NexusCare VM).
- At the VM provider: set the IP's reverse DNS (PTR) to the same `mail.` hostname.

The mail records (MX, SPF, DKIM, DMARC) come later, in step 4, because the DKIM key is generated by the server.

## 3. Install

On each VM, as root:

```shell
cd /opt && git clone -b main https://github.com/CodeXenix/XenixMail && cd XenixMail && bash install.sh --domain nexuscare.com --TZ Asia/Karachi
```

Use `--domain codexenix.com` on the CodeXenix VM, and your own time zone. The installer:

- installs Docker if needed;
- generates the database password, admin username, admin password and the safe path;
- starts the stack;
- prints the admin console address.

Run `bm default` to see the login details again.

**Keep the safe path.** The admin console only opens at `https://mail.nexuscare.com/<safe path>`; any other URL returns "Not Found". Store each server's URL, username and password in your password manager.

## 4. Add the domain and publish the mail records

In the admin console:

1. **Domain → Add domain:** add `nexuscare.com`.
2. Open the domain's DNS records and copy each one (MX, SPF, DKIM, DMARC) into the company's DNS. `bm show-record` prints them on the server too.
3. Wait until every record shows as verified. DNS changes can take up to an hour.
4. The SSL certificate is requested automatically once `mail.nexuscare.com` resolves to the server.

## 5. Mailboxes, contacts, first campaign

- **Mailboxes:** create the company's sending addresses, for example `news@nexuscare.com`. Staff can read them in a mail app (IMAP 993, SMTP 465 or 587) or in webmail at `/roundcube/`.
- **Contacts:** import the company's contact list into a group.
- **Email Marketing:** send a test email to yourself first and check it lands in the inbox, not spam.

## 6. Warm up the new IPs

A brand-new IP has no sending reputation. Sending thousands of emails on day one gets it blocked.

- Turn on **Associate IP Warmup System** for campaigns. It ramps the daily volume up over several weeks.
- Start with the most engaged contacts, and keep bounces and complaints low.
- Watch **Settings → blacklist alerts**, and check the IP on a blacklist checker weekly at first.

## 7. Day to day

- **Switching servers:** add both servers in the header's instance switcher (the stacked-servers icon) to jump between NexusCare and CodeXenix from one browser.
- **Updates:** run `bm update` on each server. It pulls the latest `main` branch and the latest core image (`ghcr.io/codexenix/xenixmail-core`), then restarts the stack. Update one server first and check it before updating the other.
- **Backups:** back up `/opt/XenixMail` on each server nightly, at least `.env`, `postgresql-data/`, `vmail-data/`, `conf/`, `core-data/` and `ssl/`. These hold the database, every mailbox, and the DKIM keys; losing the DKIM keys means republishing DNS records.
- **Status:** run `bm status` to see container health, and `bm help` for every management command.

## Shipping a new version

The servers run the image that GitHub Actions builds from `main` (`.github/workflows/core-image.yml`):

1. Rebuild the frontend into `core/public/dist` (see CLAUDE.md), then commit.
2. Merge into `main`. The workflow builds and publishes `ghcr.io/codexenix/xenixmail-core:latest`, and `:sha-<commit>` for rollbacks.
3. Run `bm update` on each server.

The first time the workflow runs, make the package public on GitHub (CodeXenix organization → Packages → xenixmail-core → Package settings → Change visibility). Otherwise each server has to `docker login ghcr.io` with a token before it can pull.
